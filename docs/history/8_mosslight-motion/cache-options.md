## Concrete implementation boundary

Create 40 fixed terrain chunks for the current 48-by-26 map. Each core covers at most 420-by-420 cache pixels. Extend its raster rectangle by two pixels on each interior edge, clamped to the full map rectangle at outer edges. Use a transparent SubViewport of exactly that raster size, translated by the negative integer world-pixel origin; keep the existing 70-pixel world sampling and `CaveArt` methods unchanged. Each chunk retains every rock/growth source whose conservative artwork support intersects its padded raster rectangle. Keep source cells in original y-major order, with all rock nodes before all growth nodes inside every chunk. Duplicating a boundary source into two chunks is necessary; its commands must remain identical world-coordinate commands. Viewport canvas transforms move child canvas items, and `UPDATE_ONCE` returns the target to disabled after one update. [Godot Viewport](https://docs.godotengine.org/en/stable/classes/class_viewport.html#class-viewport-property-canvas-transform), [Godot SubViewport](https://docs.godotengine.org/en/stable/classes/class_subviewport.html#enum-subviewport-updatemode).

Present only each nonoverlapping core using the corresponding source region of its cached texture. Use the existing premultiplied-alpha material and linear filter. Region sampling must permit the two-pixel guard to contribute to bilinear filtering, rather than clamping to the core region; a `draw_texture_rect_region` display with `clip_uv=false` is the first implementation to verify in the exact engine. Do not independently round projected chunk positions or sizes. Compute both edges from the same world transform so adjacent chunks meet at fractional camera/zoom coordinates. The outer map boundary keeps the old target's clamp behavior by omitting an outward guard. Region drawing is a supported CanvasItem operation; the precise edge pixels still require comparison. [Godot CanvasItem](https://docs.godotengine.org/en/stable/classes/class_canvasitem.html#class-canvasitem-method-draw-texture-rect-region).

Use a fixed conservative source support rectangle `cell + Rect2(-0.25, -0.65, 1.5, 3.15)` for this authored art. Source inspection shows ground fern/mushrooms extend above the cell, rock rims cross side boundaries, and ceiling vines extend to about 2.373 cells below their source origin (maximum endpoint 2.35 plus stroke radius). This envelope intentionally has slack; it is not a renderer-derived exact bound. It must be revised if art changes. A draw-call bounds tracer or native pixel comparisons should validate it before production acceptance. The two-pixel guard handles sampling; it is not a substitute for including neighboring source artwork.

Keep the existing semantic signatures. A dig changes the removed cell and four cardinal neighbors; a material change affects one cell; an occupied-cell change affects its supporting floor; building activity alone does not affect terrain. Queue redraw on the copies of changed sources only, and enable only chunks intersecting old or new support. With the fixed conservative envelope, old and new use the same support, so deletion cannot leave old vines behind. Set every dirty chunk to clear before repainting its retained local content. Coalesce multiple edits from one simulation tick into a union of dirty chunks and update them in the same frame; do not smear a dig across later frames to improve statistics. Keep the air, infrastructure, and dynamic layer order unchanged. No pan, zoom, resize, pause, ordinary simulation tick, or idle frame may invalidate terrain chunks.

On a dimension reset, free old chunk nodes, viewports and displays, clear source-to-chunk indexes and signatures, and rebuild the new domain. On a same-size/same-clock colony reset, force signature/hash observation, retaining existing surfaces only when their contents truly match. Build all initial chunks at startup; do not defer offscreen work to camera movement. Initial creation and ordinary reset remain explicit events that must be timed and checked, rather than used to conceal recurring full-cave work.

## Risks and falsification

- **Pixels and seams:** missing overhang contributors, wrong source order, clipped bilinear taps, mismatched alpha, fractional projection rounding, and wrong map-edge clamp can all change the picture. Compare the original title pixel-for-pixel; inspect full-resolution native images after every fixed dig, at chunk corners, in a second camera view, across min/max zoom, and with enlarged UI. Title parity alone does not exercise new excavation boundaries. Reject any missing vine, moss, limestone phase shift, seam, or UI change.
- **Residual frame work:** forty targets may cost more to traverse or switch than one target; drawing complete chunks without retaining source commands may reintroduce CPU geometry work. Record dirty chunk count, target pixels, changed source draw counts and terrain hashes alongside all eligible frame intervals. If the fixed unchanged workload still has repeatable topology frames above 16.7ms, reject the candidate regardless of averages or area reduction. Do not label the remaining delay as GPU fill without measurements that distinguish it.
- **Stale or delayed content:** a removed source must clear all affected old pixels, and all touched chunks must present the new terrain together. Test changes at every chunk edge/corner, occupancy addition/removal, material changes, adjacent digs in one tick, map edges, dimension resets, same-clock resets, and pan/zoom without new dirties. Repeated target rebuilds on view movement falsify the intended mechanism.
- **Scope and proof:** run the exact declared seed-42 Windows Compatibility fixture and the original eligible windows, including the 22-second 3x resume; report all over-budget frames and p50/p95/p99/max, moving-position duplicates and pose-clock progression. Retain artifact hashes and capture exclusions. Engine-input replay remains distinct from Windows OS-input and compositor timing, as recorded in `capture-review.md`. The separate browser control/UI gates remain necessary. No native or browser acceptance was performed by this assessment.

## Other mechanism families

Direct retained world-space vector nodes remove the terrain render target entirely and let viewport culling skip offscreen content. That is a useful contrasting experiment, but it rerasterizes visible detailed rock/foliage each ordinary frame and changes the existing maximum-zoom supersampling path; it risks turning local edit stalls into a steady-state cost or pixel differences. It has weaker evidence than bounded cached raster surfaces for this acceptance target.

A single persistent texture with rectangular GPU updates could preserve a one-surface display, but Godot's documented SubViewport clear/update controls do not provide a dirty-rectangle repaint contract. Painting transparent patches cannot erase old alpha by ordinary blending, and copying through CPU `get_image`/texture upload would add readback/synchronization. A custom GPU copy/update route increases implementation and compatibility uncertainty. Do not improvise `CLEAR_MODE_NEVER` as a local-erase mechanism.

A pre-rendered terrain-variant atlas can trade runtime geometry for textured quads, but preserving the current exact artwork requires accounting for world-dependent limestone phase, procedural seeds, material, all exposure combinations, occupancy, overhang order and filtering. A per-cell viewport/sprite atlas also multiplies target and composite count and makes cross-cell rock/growth ordering difficult. It is a larger art/render-system change than chunking and is not the first bounded repair.

## Coordinator variant source addendum

After the independent candidate above was complete, the coordinator supplied a four-cell-core implementation sharing a single `World2D` among all chunk SubViewports. A separate source read found world-view SHA256 `c7d4cfc242aa4af3dea86f643766ee558b4b7c9a8cd3cf4b253b3d58722a0b84`. This variant keeps exactly one retained painter pair per source cell and the original global rock/growth ordering; each viewport's integer `canvas_transform` selects its raster region, relying on Godot's canvas culling to select overlapping drawing commands. It therefore avoids duplicating command generation and boundary-source nodes and is preferable at source level if the runtime verifies culling and shared-world behavior. This addendum is not a native test or acceptance of that revision.

The variant's changed-source invalidation visits integer cells `x in [c.x-1,c.x+2)` and `y in [c.y-1,c.y+3)`, which contain the inspected authored support. Actual maximum dirty area should be measured from that larger integer halo, rather than presenting the prototype's tighter-envelope numbers as implementation measurements. Its 84 display/viewport pairs trade more target switches for smaller surfaces; the fixed native workload must decide that tradeoff.

One concrete parity risk remains in the inspected source: `_rebuild_terrain_chunks` adds two pixels of guard on every edge, including the map's exterior, whereas the old full-map texture clamps its edge texel. Those exterior guards can hold transparent or out-of-map pixels, changing linear sampling at the outer map boundary. Clamp the padded raster to the full map rectangle and derive the atlas region offset from `core.origin - raster.origin`, or verify the exact exterior pixels at minimum/wide zoom before asserting parity. The coordinator was informed of this risk. Interior atlas seams, real draw-command bounds under culling, source-canvas visibility while its original viewport is disabled, simultaneous target freshness, and reset cleanup still need the retained pixel/runtime checks.
