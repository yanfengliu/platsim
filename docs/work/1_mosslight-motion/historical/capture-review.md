## Valid routes and limits

**Root-viewport readback is conditionally valid native visual evidence.** Load the unchanged normal scene from the identified final pack in the matching Windows engine, use its ordinary GPU renderer, and save the root viewport texture after `frame_post_draw`. Godot documents that this signal follows viewport updates and that a viewport texture contains the viewport's rendered content. This can capture actual game artwork and moving settlers without reconstructing their appearance or changing gameplay. Read the root viewport, not either terrain/infrastructure cache: those subviewports exclude parts of the final scene. It establishes renderer output, not Windows compositor output or physical display cadence. [Godot RenderingServer](https://docs.godotengine.org/en/stable/classes/class_renderingserver.html#signals), [Godot ViewportTexture](https://docs.godotengine.org/en/stable/classes/class_viewporttexture.html).

**A separate Windows capture helper is also conditionally valid and more independent of the renderer.** Desktop Duplication can acquire desktop frames; Windows.Graphics.Capture can acquire a display or application window. Neither route has been exercised by this reviewer. Identify the owned window/PID, retain the actual client rectangle and pixel dimensions, and inspect for stale/black frames, unrelated windows, occlusion, DPI scaling, clipping and wrong-window selection. Run any helper under an external deadline and close its resources. API availability, token access and helper implementation remain unverified; the Windows capture picker may require user interaction. [Microsoft Desktop Duplication](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/desktop-dup-api), [Microsoft screen capture](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture).

## Required checks and false-pass risks

1. Retain hashes of the exact engine/executable, pack, observer and relevant source/export manifest, plus command line, PID, renderer and display-server identity. `native-session.cjs` only copies its executable if absent, so a filename is insufficient evidence that the cached executable matches its source. The default pack points to the old primary-checkout release; an updated-run label cannot establish that the updated pack was used. Confirm GPU startup output and reject the dummy/headless renderer. An official engine loading the pack is an instrumented native run; it does not independently validate every property of the shipped executable wrapper.
2. Retain actual keyboard/mouse actions and their observed effects, then capture active play and visibly moving settlers. Decode and inspect the full PNG at its real dimensions, including the UI; a successful `save_png` return or file existence is insufficient. Verify orientation, colors, complete frame content and that the sequence changes in the settlers' pixels. Preserve timestamps/frame IDs and original images. Sparse stills or a montage cannot prove smooth animation at natural cadence; a sequence must be described at its measured capture cadence, without invented intermediate frames.
3. Keep all readback and PNG encoding outside the measured frame-pacing intervals, including the interval crossing each capture and recovery afterward. Prefer a separate capture phase/run. Do not remove slow frames from otherwise normal gameplay. Retain contiguous, declared active-play windows for normal, wide, moving-worker and excavation contexts, with duration, frame count, median/p95/p99 and the proportion of intervals exceeding 16.67ms. A high average alone can hide choppy motion. Godot warns that viewport-to-image conversion is slow. [Godot ViewportTexture](https://docs.godotengine.org/en/stable/classes/class_viewporttexture.html).
4. Treat `frame_post_draw` samples as engine frame-boundary evidence, not a GPU completion fence or independent presentation/scanout trace. Pair unperturbed timing with actual visual inspection. The observer's `drawn.get(colonist.id, authoritative)` fallback can silently substitute simulation positions for absent draw data; missing entries must be flagged/excluded from claims about actual rendered positions. Even valid `_last_positions` values describe draw commands, not verified visible pixels or limb poses.
5. Arm a separate process deadline for each capture attempt before calling the potentially blocking API; terminate its owned capture/game tree within 30 seconds on failure. The inspected launcher uses `(duration + 30)` seconds and `child.kill()`, so it does not by itself meet the fixed capture deadline or guarantee descendant cleanup. Its exit handler only invokes tree cleanup while the direct child still appears alive. Verify owned PIDs and descendants after both success and failure, without touching shared applications. A timer in the process blocked by capture is insufficient.

## Unsupported or blocked alternatives

The existing computer-use screenshot bridge is rejected for this run after its two recorded stalls; another `Promise.race` around the same bridge does not change its blocked-event-loop failure. `PrintWindow` is a separate mechanism but is synchronous and asks the target application to render into a supplied device context, so it is neither a safe unbounded fallback nor automatically proof of the ordinary GPU frame; its pixels would need independent validation. [Microsoft PrintWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-printwindow).

PresentMon/ETW is recorded as unavailable to the current token; it is timing instrumentation, not a replacement for pixel capture. This review does not independently reproduce that access failure and does not authorize token, group or security changes. Browser screenshots, dummy-renderer exports, fabricated motion frames and state-mutating setup remain disqualified as native Windows evidence. No route is an acceptance pass until the final artifact is actually run, the resulting images are inspected, unperturbed native timing is assessed, and owned-resource cleanup is verified.

## Engine input replay boundary addendum

The coordinator reports a further failure: a Sky `press_key` call alone hung for approximately 183.9 seconds despite a 10-second timeout; no screenshot was retried, and the helper was stopped. This reviewer did not reproduce that failure. It broadens the known automation failure to input delivery and is not evidence that the game itself rejects input. The original real-input criterion in `capture-check.md` remains unchanged and unfulfilled for the proposed replacement run.

**Recommendation: proceed with a separately labeled native GPU benchmark driven by engine input replay, while retaining the native OS-input check as a gap.** Godot documents `Input.parse_input_event` as feeding artificial input events to the game, including normal `_input` dispatch, without affecting the operating system. It can therefore generate an ordinary native gameplay workload through production controls without directly editing simulation state. This is valid instrumentation for render cadence and presentation motion; it is not an OS keyboard/mouse delivery test. [Godot Input.parse_input_event](https://docs.godotengine.org/en/stable/classes/class_input.html#class-input-method-parse-input-event).

The current main scene starts with the ordinary title button focused; its gameplay key handler routes arrows, Enter, tool digits and camera keys, and its global input handler routes Escape. Exercise those routes using real `InputEventKey` press/release pairs with the fields the production handlers inspect, including `keycode`. The replay must not call `_start_game`, `_activate_cell`, button callbacks, `_input` or simulation methods directly; force focus, camera, pause or UI settings; advance clocks; or relocate settlers. Observe the results after normal event processing. If a requested workload or setting is not reached, report it as uncovered instead of repairing state from the harness. Keep the input driver separate from the read-only observer, or explicitly describe a combined harness as an input driver plus observer rather than wholly read-only.

For meaningful native results, retain exact replay/source/pack/engine hashes, GPU and window settings, the event schedule and observed transitions. Use normal wall-clock simulation, active and unpaused workload windows, and the unchanged production renderer. Record normal, wide, moving-worker and excavation contexts rather than assuming emitted keys reached them. Separate capture readback from timing, assess frame distributions and continuous drawn travel/poses, and inspect the actual resulting native pixels. Engine replay does not excuse any deadline, capture, artifact-identity or owned-process cleanup requirement above. A synthetic setup sequence is acceptable only under that truthful label; it must not be represented as the real-input prerequisite having passed.

The owner's requested outcomes remain at least 60fps Windows rendering, smooth animation, scalable UI and Escape/Settings behavior. Native replay measurements can support the first two and exercise the native UI's in-engine event handling. The mandated headless browser checks must still use real keyboard/mouse controls and inspect rendered layouts at all required sizes and breakpoints. Passing those browser checks establishes browser control/layout behavior; it cannot establish Windows focus, OS event delivery, mouse coordinates under desktop DPI, native activation or native input latency. No browser pass should erase that distinction.

A shipped-executable startup/print-FPS crosscheck establishes that the identified executable launches and renders its initial scene. It does not establish sustained gameplay frame pacing. Running its exact pack in the matching full engine supplies stronger native workload evidence, but a different engine binary is still an instrumentation boundary: retain matching engine/export versions, renderer/settings and hashes, and attribute measured results to that instrumented run. Neither result is independent compositor/scanout timing. Sparse PNGs plus smooth coordinate samples also do not become a recorded natural-cadence visual pass merely because the driver changed.

The acceptable report is therefore: native GPU workload measurements and renderer pixels from the identified pack under engine-level input replay; browser controls and layouts verified separately when those gates finish; final Windows OS-input delivery and independent presentation timing remain unverified. Do not mark the original native real-input capture criterion complete or claim comprehensive shipped-executable interaction acceptance from this route. This addendum assesses the proposed method only; no replay implementation or runtime output was reviewed here, and no source outside this review record was edited.
