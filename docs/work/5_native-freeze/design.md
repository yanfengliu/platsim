# Native rendering investigation

The investigation starts from delivered source 9c1fe74778eff04b13030435263422a314bb7072 and the original reported Windows artifact 7f19f971a4bd37443f544b118242939ab7372ae578ea6aa5e5188925dd239baf. No native graphics workload or driver API was invoked on this workstation. The independent native_backend_audit lane read repository code, exact Godot 4.7.2 source and previous native logs, and parsed preserved shader caches offline.

## Confirmed incident and access facts

Explorer UserAssist records the primary platsim executable at 21:37:25.940 PST on November 7. Its format was interpreted against the [UserAssist forensic parser](https://github.com/EricZimmerman/RegistryPlugins/blob/master/RegistryPlugin.UserAssist/UserAssist.cs). The game log rotated at that time and its new file is empty. The owner says the image froze and they held the power button. The event's power-button timestamp converts to 21:40:18.534 PST; boot records begin at 21:41:22. This establishes neither a spontaneous reboot nor a power-supply fault.

Explicit access checks fail for LiveKernelReports and protected WER content. The session is not running with an administrator token, even when the tool's filesystem sandbox escalation is allowed. Earlier suppressed errors therefore concealed missing evidence. BAM launch metadata also denied access; the separate UserAssist path was readable. The accessible minidump is dated July 28 and is not attributed to this incident.

TdrLevel=3 enables recovery, while TdrDelay=30 and TdrDdiDelay=30 override Microsoft's documented defaults of 2 and 5 seconds. These values can change recovery timing; they do not establish a trigger. Nothing was changed. [Microsoft TDR registry documentation](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/tdr-registry-keys).

## Native audit findings

Previous successful native logs identify desktop OpenGL 3.3, NVIDIA RTX 4090 and driver 616.64. The project selects Compatibility, whose Windows default is opengl3 in [Godot main.cpp](https://github.com/godotengine/godot/blob/4.7.2-stable/main/main.cpp#L2403). The empty incident log cannot directly prove the crashed process reached that exact backend.

Those successful logs also report failure to create the shader-cache directory. That disables persistent shader caching and leaves a significant difference from a normal standalone launch. The user's existing AppData cache was preserved unchanged, with timestamps around 15:20 earlier that day. All five GLSC v3 containers parse exactly against [Godot shader_gles3.cpp](https://github.com/godotengine/godot/blob/4.7.2-stable/drivers/gles3/shader_gles3.cpp#L543): 992,458 bytes, 20 variants and 22 program binaries. Canvas/Copy/Feed/Post/Scene variant counts are 1/13/1/1/4, matching the engine. All inventory hashes match; no truncated fields, impossible lengths, duplicate specialization keys or trailing data exist. The largest binary is 382,249 bytes. This excludes malformed container lengths and container truncation in the preserved files. It cannot validate opaque NVIDIA binary semantics or prove that the incident process loaded these files. The driver receives those blobs through glProgramBinary; shader-key hashes include GL vendor/renderer/version but cannot be reversed into an originating driver version. Reproducible parser and JSON results remain in ignored evidence.

The application render graph has no evident feedback cycle. Terrain painters use a private World2D shared by chunk viewports; displayed chunk textures live in the main canvas. Each viewport has its own default World2D, so infrastructure does not render its own displayed texture. Dimension changes remove and queue old painters, viewports and display nodes for deletion; Godot's viewport destructor unregisters the world, clears texture back-pointers and frees its viewport RID. The application supplies no custom native shaders or GL calls.

Transparent caches allocate both RGBA8 and DEPTH24_STENCIL8 even when 3D is disabled, according to [texture_storage.cpp](https://github.com/godotengine/godot/blob/4.7.2-stable/drivers/gles3/storage/texture_storage.cpp#L2560). Eighty-four terrain targets plus infrastructure therefore carry approximately 94.5 MiB of attachments, before the main framebuffer, other textures/buffers and driver overhead. This startup burst is finite; it is not proof of exhaustion or a leak.

Godot's [Windows OpenGL manager](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/windows/gl_manager_windows_native.cpp#L170) also associates the executable with an NVIDIA application profile and changes OpenGL threading/windowed G-SYNC settings before graphics context creation. The editor engine and exported executable have different identities, so observer testing does not establish identical profile behavior. No NVIDIA profile API was called during this investigation, and this difference is not a demonstrated cause.

## Upstream reports and rejected shortcuts

Godot issue [122828](https://github.com/godotengine/godot/issues/122828) described a similar 4.7.2 NVIDIA failure with actual TDR evidence, but involved Mono/ANGLE, a different card/driver and black displays. Its author later withdrew the Godot attribution and closed it. It cannot establish this incident's cause. Issue [122221](https://github.com/godotengine/godot/issues/122221) requires editor embedding and reports clean standalone behavior, so its conditions do not match. Other broadly similar startup reports lack an established matching reproduction. NVIDIA's [616.86 hotfix notes](https://nvidia.custhelp.com/app/answers/detail/a_id/5906/~/geforce-hotfix-display-driver-version-616.86) do not identify a Godot/OpenGL freeze fix; no driver update or rollback was attempted.

Connected projects are local only, and the repository has no registered self-hosted runners. Standard [GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) could exercise native Godot with a software renderer in a separate VM. Such a run would not reproduce the workstation's proprietary NVIDIA binary-cache or driver path and cannot establish their innocence. No remote GPU capacity is configured or provisioned. No remote workload was dispatched merely to obtain another non-equivalent passing test.

## Remaining decisive evidence

The owner approved protected incident report collection on November 8. The independently reviewed collector reads system data without driver/registry/ACL/network changes and uses fresh per-run output directories. Dump copying is restricted to the incident time window and 512 MiB; WER copying is limited to 64 reports, 256 KiB per file and 8 MiB total. Skips and access errors are retained. Report-folder timestamps and actual report EventTime must be checked separately: files queued after reboot can describe older failures.

Without an incident dump/report or a controlled reproduction on a separate matching GPU machine, the trigger remains unconfirmed. A driver/presentation hang is a hypothesis, not a diagnosis; the available evidence does not distinguish it reliably from another system-level hang.

## Administrator collection and follow-up, November 8

The exact reviewed collector (SHA256 9b6712355a006a345b526d1126139f4263f40d76ad2aa11eb1bd72b32843d0c5) ran once with the owner's explicit approval and a Windows administrator token. It exited 0 after about one second of collector execution. Its inventory reports no access errors or budget skips, 44 copied WER reports totaling 1,067,418 bytes, and zero incident-window dump bytes. Every copied report's size and hash matches its inventory entry. The script did not run a game, invoke a graphics driver, change settings or upload data.

LiveKernelReports contains a January 2025 NDIS dump; Minidump contains the July 2026 minidump. Neither is incident evidence. All 44 collected WER reports are historical: 43 LiveKernelEvent reports and one July BlueScreen report. Their EventTime range is January 13, 2025 through October 24, 2026 UTC; the newest converts to October 23 at 18:59:30 PDT. All queue files were modified around November 8 at 08:01 PST, illustrating why modification time alone must not attribute a report to this freeze. No copied report has an incident-time EventTime.

The historical codes comprise 14 reports with 0x1A8, 27 with 0x1B8, one with 0x141, one with 0x15E and one with 0xEF. Microsoft's [0x1A8](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/bug-check-0x1a8--video-dxgkrnl-black-screen-livedump) and [0x1B8](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/bug-check-0x1b8--video-miniport-black-screen-livedump) documentation describes diagnostic live dumps, including manual/internal triggers; these codes alone do not prove a driver defect. The [0x141 display-engine timeout](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/bug-check-0x141---video-engine-timeout-detected) is dated March 15, not November 7. No historical report establishes this incident's cause.

An uncapped metadata enumeration found 500 archive folders and 44 queue folders. None matches Mosslight, Godot or dwm, and none was created on or after the incident; the newest archived folder was created November 6. The configured crash-control paths use the already inspected standard Minidump directory; MEMORY.DMP is absent. The current-user CrashDumps directory has no Mosslight/Godot/dwm dump, and the folder configured for eight NVIDIA application dump handlers does not exist. These are location-specific observations, not proof that a record never existed or that every possible destination has been searched.

Saved event queries covered November 7 from 21:00 to 22:15 PST. WerKernel/Operational, WER-PayloadHealth/Operational and WER-Diag/Operational returned explicit NoMatchingEventsFound, not permission errors. Kernel-WHEA/Operational returned 12 records, all after boot began, and Kernel-WHEA/Errors returned one record at 21:41:28.959 PST. Offline parsing of that 952-byte CPER record found severity 2 (corrected), a valid reporting timestamp at 21:41:28 PST, Precise=false, and header flags zero. The [WHEA header](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddk/ns-ntddk-_whea_error_record_header), [severity](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddk/ne-ntddk-_whea_error_severity) and [timestamp](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddk/ns-ntddk-_whea_timestamp) definitions support that interpretation. Together with the already recorded corrected PCIe root-port event, this is insufficient to attribute a hardware failure before the forced restart. No debugger or hardware probe was needed.

Collection approval is fulfilled. The remaining blocker is missing causal evidence. Existing records cannot identify a frozen native stack, graphics command or responsible module, so no specific renderer, shader-cache, driver or hardware defect is claimed fixed. Raw collection, inventories, timestamp summaries and log extracts remain local under ignored output/native-freeze; only this sanitized account and review are committed.
